## How It Works

With an npm token, anyone who gets the token can publish your packages, until you revoke it. With trusted publishing, you tell npm once which workflow of which repository may publish a package. At each publish, the CI job gets a short-lived OIDC token from GitHub, GitLab or CircleCI proving which repository and workflow it runs, and npm exchanges it for a publish authorization. There is no secret to store nor to rotate.

npm also adds the **provenance** of the package, on GitHub and GitLab: its page on npmjs.com links each version to the commit and the run that built it, for a public package published from a public repository. CircleCI gives none.

A configuration says what the workflow may do: **publish directly**, **stage** the versions for [approval](./staged-publishing.md), or both. Relizy needs no option for trusted publishing: in a job that can get an OIDC token, without npm token, it publishes to npmjs.org with it.

## Setup

### 1. Give the Job Its OIDC Token

The workflows generated by `relizy init` already do it.

::: code-group

```yaml [GitHub Actions]
jobs:
  release:
    permissions:
      contents: write
      # npm trusted publishing (OIDC)
      id-token: write
    steps:
      - uses: actions/checkout@v7
        with:
          fetch-depth: 0
      # Updates npm to 11 when it is older than 11.15.0
      - uses: relizy/action@v2
```

```yaml [GitLab CI]
# The relizy component requests the NPM_ID_TOKEN id token and updates npm
include:
  - component: gitlab.com/relizy/relizy/release@2
```

```yaml [GitLab CI (job written out)]
release:
  # npm trusted publishing (OIDC)
  id_tokens:
    NPM_ID_TOKEN:
      aud: npm:registry.npmjs.org
  before_script:
    # Trusted publishing needs npm 11.5.1 or later, staged publishing 11.15.0
    - |
      node -e "const [a, b] = process.argv[1].split('.').map(Number); process.exit(a > 11 || (a === 11 && b >= 15) ? 0 : 1)" "$(npm --version)" || npm install -g npm@11
  # ... install
  script:
    - pnpm exec relizy release --yes
```

```yaml [CircleCI]
# The job gets its ID token by hand, relizy detects NPM_ID_TOKEN
steps:
  - run:
      name: Get the npm ID token
      command: |
        NPM_ID_TOKEN=$(circleci run oidc get --claims '{"aud":"npm:registry.npmjs.org"}')
        echo "export NPM_ID_TOKEN='$NPM_ID_TOKEN'" >> "$BASH_ENV"
  - run: pnpm exec relizy release --yes
```

:::

### 2. Publish the First Version of a New Package

npm cannot create a package with trusted publishing: the package must exist before its trusted publisher does. Publish the first version of a new package from your machine (`npm login`, with your 2FA), or with an npm token while tokens can still publish (see [Moving off npm tokens](./npm-token-migration.md)), then set up trusted publishing. Before the bump, Relizy warns about the packages that are not on npm yet and says how to create them.

### 3. Set Up the Trusted Publishers

```bash
relizy trust
```

[`relizy trust`](./../cli/trust.md) creates the trusted publisher of every public package with your npm login and **one 2FA**: the web page of npm opens in the browser (security key, passkey or code). It reads the workflow file, the repository and the environment of the job itself: nothing to repeat in the config, nothing to fill in on npmjs.com. `--dry-run` tells what it would do, and running it again is harmless (an existing configuration is kept).

It needs npm 11.15.0 or later, and it is never run by [`relizy init`](./../cli/init.md) (it needs your login and a 2FA). On a CircleCI pipeline written by hand, give its identifiers as flags (`--circleci-org-id`, `--circleci-project-id`...), see [CircleCI](#circleci).

Then remove `NPM_TOKEN` from the secrets, or keep it for the first publish of the next new packages.

::: warning A new configuration expires
npm removes a trusted publisher configuration that no successful publish used within 2 days. `relizy trust` lists the packages it set up with no release pending: run it again just before their next release.
:::

## The Calling Workflow and the Environments

npm matches the **calling** workflow: the file that is run by the event (`release.yml`), not a reusable workflow it calls. On GitLab, it is the top-level pipeline file (`.gitlab-ci.yml`), even when the job is in an included file. `relizy trust` takes the file name for you.

A configuration can also name an **environment** (a GitHub environment, a GitLab environment). It must be the one of the job that publishes. `relizy trust` reads it from the workflow, and `--env <name>` overrides it. `--repo` (GitHub) and `--project` (GitLab) replace the repository of the git remote.

## Permissions and Several Configurations

A configuration allows **direct publish**, **staged publish**, or both. `relizy trust` follows [`publish.staged`](./../config/publish.md#staged):

| `publish.staged`                   | The configuration of the package allows |
| ---------------------------------- | --------------------------------------- |
| `false` (the default)              | Direct publish                          |
| `true`, or `{ packages }` matching | Staged publish                          |
| `{ tags }` (depends on the tag)    | Both                                    |

It then proposes the `publish.staged` value the configurations ask for, and writes it in the config after a confirmation. A configuration that only allows staging makes a direct publish fail with `E_STAGE_REQUIRED`, see [Staged publishing](./staged-publishing.md#e-stage-required).

A package can have several configurations (several workflows, or several environments): `relizy trust` reports a configuration of the same workflow with other permissions or another environment as `differs`, and `--replace` revokes and recreates it after a confirmation.

### Making npm Enforce Staging

By default, Relizy decides what is staged, from `publish.staged`: nothing stops the workflow from publishing directly if the config changes. To make npm refuse a direct publish of the stable versions, split the release workflow into two jobs by **trigger** (the environment of a job is fixed before Relizy computes the tags), each with its own environment and its own configuration:

- a job for the stable releases, in the environment `npm-staged`, whose configuration only allows staging;
- a job for the prereleases and the canaries, in the environment `npm-direct`, whose configuration only allows direct publish.

`relizy trust` reads the two environments in the workflow and creates one configuration of each per package. The environments can carry protection rules. A run is one channel: a stable release that also carries a prerelease package stages it too.

::: warning Manual setup
`relizy init` does not generate this variant yet: write the two jobs yourself. It needs several trusted publisher configurations per package, which the npmjs.com website and the npm changelog announce (up to 10), but which the documentation of the npm CLI does not confirm yet: check that `relizy trust` accepts the second configuration of a package.
:::

## A Monorepo

The trusted publisher is set per package, and `relizy trust` does them all in one run, with one 2FA (check "skip 2FA for the next 5 minutes" on the page of npm when it offers it). A package that is not on npm yet is reported as `missing`: publish its first version, then run `relizy trust` again.

## Auth Modes

Relizy reads from the environment how each registry authenticates, and tells it in the events and the report when a run stages (`auth`, and the `publish_auth` output):

| Mode    | When                                                                                                     | What it can do                                                             |
| ------- | -------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| `oidc`  | npmjs.org, no token, and the job can get an ID token                                                     | Stage and publish directly. Never list, approve, reject nor `relizy trust` |
| `token` | A token is set for the registry (`RELIZY_NPM_TOKEN`, `NPM_TOKEN`, `NODE_AUTH_TOKEN`, a registry token)   | Stage, and publish directly until January 2027. Never approve              |
| `npmrc` | No token and no ID token: whatever the `.npmrc` files hold (a login session, a token written by the job) | Everything locally, and the approval with your 2FA                         |

With a token and an ID token at once, npm tries trusted publishing first and falls back to the token. Relizy keeps the token behavior (it checks it with `whoami`) and tells in one line that the secret can go once `relizy trust` is done. Another registry than npmjs.org is always `npmrc` or `token`: OIDC is npmjs only.

`actions/setup-node` with a `registry-url` and without token fills `NODE_AUTH_TOKEN` with a placeholder (`XXXXX-XXXXX-XXXXX-XXXXX`): Relizy does not take it for a token. You need no `registry-url`.

## What Relizy Checks

Before the bump, the [safety check](./../config/publish.md#safetycheck) of the publication does not run `npm whoami` with trusted publishing (it does not work with OIDC). Instead:

- the npm that publishes must do the OIDC exchange (11.5.1 or later), and 11.15.0 or later to stage. Otherwise the release stops before the bump with the fix. pnpm 10 and earlier publish through npm; pnpm 11 and later publish by themselves.
- **the pre-flight**: for each package the run publishes, Relizy does the exchange npm will do, four packages at a time, and throws the token away. It warns when npm does not trust the job, naming the package, the repository, the calling workflow, the environment and the fixes: `relizy trust`, the calling workflow (not a reusable one), the environment, a configuration unused for 2 days. In `relizy release` it runs right after the bump, on the packages the release publishes only. These are warnings: a run that would work is never stopped.
- a package that is not on npm yet gets the way to create it.
- a GitHub self-hosted runner or a GitLab self-managed instance gets a warning, as npm does not support trusted publishing there.
- a publish that still fails with `ENEEDAUTH` says that npm did not trust the job, instead of the misleading error of npm.

With a token, one warning per run: direct publishing with a granular token ends in January 2027, see [Moving off npm tokens](./npm-token-migration.md). Without npm token nor OIDC token in a CI, the authentication error tells both ways to publish, trusted publishing first.

`--no-safety-check` and [`publish.safetyCheck: false`](./../config/publish.md#safetycheck) silence all of it.

## Package Managers

- **npm**: trusted publishing from npm 11.5.1, staging from 11.15.0.
- **pnpm**: pnpm 11 and later do the exchange themselves, pnpm 10 and earlier publish through npm.
- **yarn classic and bun**: they cannot do the exchange. Without token, Relizy packs with the package manager and uploads the tarball with npm (the same fallback as [staging](./staged-publishing.md#per-package-manager)), so they publish with trusted publishing too. With a token, they keep their own publish command. The upload runs no `prepublishOnly`, `publish` nor `postpublish` script.
- **yarn berry**: `yarn npm publish` does the exchange itself, from Yarn 4.10 (GitHub and GitLab) and 4.15 (CircleCI). Relizy does not change its publish.

## CircleCI

CircleCI cloud runners are supported by npm. The job has no ID token by default: request it with the audience of npm, in the variable npm reads.

```bash
export NPM_ID_TOKEN=$(circleci run oidc get --claims '{"aud":"npm:registry.npmjs.org"}')
```

Relizy detects `CIRCLECI` with `NPM_ID_TOKEN`. A CircleCI pipeline is written by hand, so the git remote does not give its identifiers to `relizy trust`. Find them in CircleCI and give them as flags:

| Flag                                | Where in CircleCI                       |
| ----------------------------------- | --------------------------------------- |
| `--circleci-org-id`                 | Organization Settings > Overview        |
| `--circleci-project-id`             | Project Settings > Overview             |
| `--circleci-pipeline-definition-id` | Project Settings > Project Setup        |
| `--circleci-vcs-origin`             | The repository: `github.com/owner/repo` |
| `--circleci-context-id`             | Organization Settings > Contexts        |

```bash
relizy trust --circleci-org-id <id> --circleci-project-id <id> \
  --circleci-pipeline-definition-id <id> --circleci-vcs-origin github.com/owner/repo
```

npm gives no provenance from CircleCI. Relizy cannot tell a self-hosted runner there (no variable says it), so it never warns about it.

## Limits

- **npmjs.org only**: another registry (GitHub Packages, a private registry) still needs its token.
- **Supported runners only**: GitHub-hosted runners, GitLab.com shared runners and CircleCI cloud runners. npm does not support self-hosted runners nor GitLab self-managed. Relizy warns about a GitHub self-hosted runner and a GitLab self-managed instance (a self-hosted runner on gitlab.com cannot be told).
- **Existing packages only**: trusted publishing cannot create a package, see [Setup](#setup).
- **No approval nor listing**: a CI under trusted publishing can stage and publish, never list, approve nor reject staged versions.
- **No provenance for a private repository**, nor from CircleCI: the package is published, without provenance.

See the [npm documentation](https://docs.npmjs.com/trusted-publishers).
