# Plan v2

## Next v2.x

- [ ] Notifications Microsoft Teams (à essayer) : webhook d'un Workflow créé depuis le modèle « Send webhook alerts to a channel » (les Office 365 Connectors sont retirés depuis mai 2026). Relizy construit l'Adaptive Card (titre, sections par groupe, boutons Release / Changelog) comme les blocs Slack, et accepte l'URL en clair ou en base64 (`RELIZY_TEAMS_WEBHOOK_URL_B64`, une variable masquée GitLab refuse `?`, `&`, `%`).
- [ ] Version racine qui évolue aussi en mode `independent` (aujourd'hui elle ne bouge pas). Fonctionnalité à part : décider à quoi correspond cette version (le max des paquets ? un bump à chaque release ?) et ce qu'elle produit (tag `v*` ? changelog racine ?).
- [ ] Publication npm sans token (trusted publishing OIDC) et provenance.
- [ ] Refacto du code (reporté du nettoyage v2, sans changement de comportement) :
  - [ ] Squelette commun des commandes : `bump`, `changelog`, `publish`, `provider-release`, `social` et `pr-comment` répètent le chargement de la config, l'UI (`createCommandUi`), le `try/catch` (annulation, hook `error:*`, `ui.fail`). Un helper `runCommand()` dans `core`. Les copies ont divergé : `social` ne lance pas `error:social` sur une erreur inattendue, `pr-comment` ne lance aucun hook, `provider-release` et `social` renvoient leur erreur au lieu de la lever. `release` reste à part (rapport, commentaire de PR).
  - [ ] Boucle des version groups commune : `changelog`, `publish`, `provider-release` et `social` recopient `hasVersionGroups` / `resolveVersionGroups` / `getGroupBumpResult` / groupe sauté. Un générateur dans `groups.ts`, une entrée sans groupes.
  - [ ] Ne plus recharger le fichier de config dans les sous-commandes de `release` : avec un `baseConfig` résolu (hors groupes), `loadRelizyConfig` relance c12 et dotenv à chaque sous-commande. Fusionner les overrides sur le `baseConfig`, comme pour les configs de groupe, puis retirer les arguments redondants que `release` passe à ses sous-commandes.
  - [ ] Flux GitHub et GitLab unifiés : `github.ts` et `gitlab.ts` répètent le contrôle du token, la sélection des paquets, les tags, le changelog, l'IA et le résumé, en mode unified comme independent. Une boucle commune avec un adaptateur par provider (création de la release, payload).
  - [ ] Exécution git unique : `git()` / `tryGit()` existent en plusieurs copies (`ci.ts`, `commitlint/git.ts`, `ci-workflow.ts`), plus une douzaine d'`execSync` en chaînes shell. Un `git-exec.ts` sur `execFile` (sans shell, donc sans échappement), branché sur le cache git.
  - [ ] Découpage des gros fichiers : le bloc affichage et confirmation de `version.ts` (~240 lignes) vers `bump-prompt.ts`, la planification des bumps hors de `repo.ts`, `createCommitAndTags` (~200 lignes) en étapes (fichiers, message, tags), `npm.ts` en trois (registres et `.npmrc`, versions publiées, publication).
  - [ ] Tests : les builders de dépôts git temporaires sont écrits six fois (`release-groups.git`, `commitlint`, `tags.git`, `catalogs.git`, `package-commits.git`, `commitlint-git`), un helper partagé existe dans `src/mcp/__tests__/helpers.ts`. Même chose pour les fabriques de commits (`createMockCommit` trop étroit) et de configs de groupes, et pour `process.stdin.isTTY` basculé à la main au lieu de `setInteractiveTerminal`.
  - [ ] `tests/e2e` : ses 60 tests mockent tout sauf `release.ts` et ne couvrent qu'une ligne que les autres specs n'atteignent pas (le contrôle de la branche distante avec `--no-publish` et le push actifs, `release.ts:406`). Ajouter ce test à `release.spec.ts`, puis supprimer le dossier.
  - [ ] Détection de la CI : `isInCI()` (`utils.ts`) et `isCi()` (`release-ui.ts`) ne lisent pas les mêmes variables (`CI=1` d'un côté, `VERCEL` ou `BUILD_ID` de l'autre). À fusionner, en vérifiant le rendu choisi (`pretty` ou `ci`) pour chaque fournisseur.
- [ ] (Peut-être, après les travaux ci-dessus) Action GitHub officielle (`relizy/action`) et composant GitLab CI : installation, tokens, outputs prêts. Il faudra update la homepage pour ça ! Coût : un repo public dédié (`relizy/action`, organisation `relizy` à créer) et un projet gitlab.com publié dans le catalogue CI/CD, synchronisés à chaque release (tags `v2.x.y`, `v2` déplacé), avec leurs secrets.
